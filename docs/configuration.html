Configuration

All user-facing settings live in the USER CONFIGURATION block of geoaquacrop_plotting/config.py. It is the only module in the package with no internal dependencies, so editing it cannot break an import cycle.

The full generated reference for every constant on this page is in API Reference.

How the data paths are found

The simulation and preprocessing outputs live in checkouts that sit beside this project:

<workspace>/
├── geoaquacrop-preproc/       # climate, crop calendar, SPAM grids
├── geoaquacrop-simulate/      # summary and daily result pickles
└── Geoaquacrop-visualizer/   # this project

config.py resolves <workspace> at import time:

  1. If the GEOAQUACROP_ROOT environment variable is set, it is expanded, made absolute, and used as-is.

  2. Otherwise _find_workspace() walks up from config.py’s own directory, and then up from the current working directory, returning the first ancestor that contains a geoaquacrop-preproc folder.

  3. If neither search finds it, the conventional sibling-of-the-project-root location is assumed so the error message can name it.

That covers a source checkout, an editable install, and a plain pip install . into site-packages. To point the app at data somewhere else, either set the environment variable:

export GEOAQUACROP_ROOT=/path/to/folder/holding/geoaquacrop-preproc

or replace the four input paths below with absolute ones.

Important

If geoaquacrop-preproc is not found under the resolved workspace, importing config raises FileNotFoundError immediately, naming the path it looked for and every directory it searched from. Startup fails at import, before Dash is constructed — there is no half-initialised state to diagnose.

Path constants

SUMMARY_PKL   = <workspace>/geoaquacrop-simulate/outputs/summary_results_<stamp>.pkl
DAILY_PKL     = <workspace>/geoaquacrop-simulate/outputs/daily_results_<stamp>.pkl
GEOJSON_PATH  = <workspace>/geoaquacrop-preproc/inputdata/region_boundary.geojson
PROCESSED_DIR = <workspace>/geoaquacrop-preproc/processed
EXPORT_DIR    = <base>/outputs/exports

The pickle filenames carry the timestamp of the simulation run that produced them, so point SUMMARY_PKL and DAILY_PKL at a different run by editing the stamp.

GEOJSON_PATH is the only source of the region outline. Nothing is copied into the package: the file is read once at import and thinned in memory, so changing it changes what the maps draw on the next start.

EXPORT_DIR is resolved separately from the input paths, and does not follow GEOAQUACROP_ROOT. Its <base> is the directory holding the geoaquacrop_plotting package — the project root in the flat layout, src/ in the src layout — except when that directory is site-packages or dist-packages, in which case the current working directory is used so exports never land inside an installed environment. The directory is created on import of data if it does not exist.

Display constants

Constant

Default

Description

CELL_RES

0.05

Grid cell resolution in decimal degrees. Must match the preprocessing step — grid draws each cell as a square of this size centred on the cell coordinates, so a mismatch produces overlapping or gapped polygons.

PORT

8050

TCP port for the Dash development server.

MAP_HEIGHT

550

Height in pixels of the choropleth map panels. Also the default canvas height used by get_auto_zoom().

TS_HEIGHT

400

Height in pixels of the time series panels.

BOUNDARY_SIMPLIFY_EPS

0.004

Ramer–Douglas–Peucker tolerance in decimal degrees (~400 m) applied to the region outline at startup. Raise it for a coarser, lighter outline; lower it for a crisper, heavier one. See Region boundary.

BOUNDARY_URL

'/region-boundary.geojson'

Path the thinned outline is served from on the Dash server. Both boundary, which registers the route, and mapbox_layers(), which points the map layer at it, read this one constant.

IRR_MAP maps the irrigation names used in the simulation output ('rainfed', 'irrigated') to the two-letter codes used in the crop calendar and SPAM variable names ('rf', 'ir'). It is shared by spam_vars_for_crop(), get_cropcal_summary(), and build_input_ts().

Variable registries

Three module-level dictionaries define which variables are available in the UI and how they are displayed. Adding an entry is enough to make a variable appear — but a map or daily variable must also be listed in one of the group constants in styles.py (_YIELD_VARS, _WATER_VARS, _WP_VARS, _FLUX_VARS, _SOIL_VARS, _CROP_VARS) to be reachable from a sidebar accordion.

MAP_VARIABLES

Controls the simulation output choropleth map. Each key is a column name in the summary pickle. Each value is a dict with:

  • label — display name used in the colour bar and dropdowns.

  • colorscale — Plotly colour scale for mean aggregation.

  • sum_colorscale — Plotly colour scale for sum aggregation.

  • default_agg — aggregation used when All years is selected and no explicit override is set ('mean' or 'sum').

DAILY_VARIABLES

Controls the daily time series panel and the export modal. Each key is a column name in one of the daily pickle tables. Each value is a dict with:

  • label — display name, also used as the y-axis title and as the NetCDF long_name; the parenthesised trailing part becomes the NetCDF units attribute on export.

  • table — source table, either 'water_flux' or 'crop_growth'.

  • color — hex colour for the line trace and the mean ± std band.

CLIMATE_VARIABLES

Controls the climate input choropleth and time series. Each key matches both a NetCDF variable name and the <Variable> part of the filename in PROCESSED_DIR. Each value is a dict with:

  • label — daily y-axis label (e.g. 'Precipitation (mm/day)').

  • map_label — choropleth hover label (e.g. 'Precipitation (mm/year)').

  • unit — colour bar unit string.

  • color — hex colour for the time series line.

  • colorscale — Plotly colour scale for the choropleth.

The two labels differ because the two views aggregate differently. The time series always plots daily values; the map reduces over the selected period, and get_climate_map_values() sums Precipitation and ReferenceET while it averages the two temperature variables. Adding a new accumulating variable therefore means adding its key to the _SUM_VARS tuple in queries.py as well, and to the matching branch in patch_input_map_data() that picks the (total mm) rather than the (daily mean) colour-bar caption.
